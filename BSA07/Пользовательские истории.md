# БСА07_Пользовательские истории (User Stories)

## 1. Что такое пользовательская история?

**Пользовательская история (User Story, US)** — метод, позволяющий быстро понять и кратко зафиксировать потребности пользователей в системе. Это краткое описание функциональности и/или качества, необходимых конкретной заинтересованной стороне для получения ожидаемой пользы.

### 1.1 Характеристики User Story

| Характеристика   | Описание                                                                    |
| ------------------------------ | ----------------------------------------------------------------------------------- |
| **Краткий**       | Помещается на небольшой карточке или стикере |
| **Простой**       | Легко читается и понимается                                 |
| **Ценный**         | Соответствует потребности пользователя          |
| **Атомарный**   | Описывает одну функцию или одно качество         |
| **Бизнесовый** | Написан бизнес- или пользовательским языком   |

### 1.2 Структура User Story

| Элемент                              | Описание                                                                           |
| ------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Заголовок**                | Активное глагольное выражение цели                          |
| **Тело**                          | Как [роль] я хочу [сделать], чтобы [получить выгоду] |
| **Критерии приемки**   | Условия, определяющие границы истории                     |
| **Тестовые сценарии** | Описание того, что должно быть проверено                 |

### 1.3 Формат тела User Story

> **Как** [роль пользователя]
> **я хочу/могу** [сделать то-то и то-то]
> **чтобы** [получить какую-то выгоду]

**Пример:**
*Как зритель кинотеатра, я хочу купить билет онлайн заранее, чтобы посмотреть кинофильм в удобное время.*

## 2. Критерии приемки и тестовые сценарии

### 2.1 Критерии приемки (Acceptance Criteria)

Определяют границы истории и дают понимание, какое поведение должно обеспечивать решение.

**Формат (Given-When-Then):**

| Компонент                       | Описание                                                 |
| ---------------------------------------- | ---------------------------------------------------------------- |
| **Given** (Предусловие) | Роль пользователя, обстоятельства  |
| **When** (Действие)        | Выполнение действий пользователем |
| **Then** (Результат)      | Какая ценность получена                     |

### 2.2 Тестовые сценарии (Test Scenarios)

Описание того, что должно быть проверено:

- На каких данных
- Какие установки
- Какие действия
- Какой ожидается результат

## 3. Методология 3C

| Этап                                            | Описание                                                                                                                          |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **Card** (Карточка)                   | История формулируется компактно, чтобы помещалась на карточке или стикере |
| **Conversation** (Обсуждение)       | История служит стартом для обсуждения между заинтересованными сторонами   |
| **Confirmation** (Подтверждение) | Получение согласия от пользователя и команды разработки                                  |

---

## 4. Критерии INVEST

| Критерий                                          | Описание                                                                                                 |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **I**ndependent (Независимость)        | Стремиться к независимости US друг от друга                                   |
| **N**egotiable (Обсуждаемость)         | Оставлять возможность обсуждения с пользователем и командой |
| **V**aluable (Ценность)                     | Выявлять пользу действий пользователей                                        |
| **E**stimable (Оценка трудозатрат) | Возможность оценить затраты на реализацию                                   |
| **S**mall (Компактность)                | Автономность и небольшой размер                                                      |
| **T**estable (Тестируемость)           | Наличие критериев приемки и тестовых сценариев                          |

---

## 5. Преимущества и ограничения

### 5.1 Преимущества

| Преимущество                   | Описание                                                                                     |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| **Небольшие части**    | Реализуемые и тестируемые фрагменты функциональности |
| **Понятность**             | Легко понимаются заинтересованными сторонами                |
| **Фокус на ценности** | Позволяет улучшать понимание процесса                              |

### 5.2 Ограничения

| Ограничение                                | Описание                                                                                                       |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Требует контекста**           | Необходимо понимание общей картины                                                      |
| **Неполнота документации** | Не дают документацию, достаточную для реализации                             |
| **Краткосрочность**              | Предназначены для быстрой фиксации, не для длительного хранения |
